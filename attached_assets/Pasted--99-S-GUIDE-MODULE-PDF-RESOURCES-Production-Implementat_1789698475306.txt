# 99'S GUIDE — MODULE PDF RESOURCES
## Production Implementation
### Module Resources + Large PDF Uploads up to 200 MiB
### Database + R2 + Backend + Console + Modules UI
### STRICT SCOPE — DO NOT TOUCH UNRELATED FEATURES

We are adding a new production feature to 99's Guide.

The application currently has exactly seven academic Modules:

1. CA  — Clinical Attachment
2. ID  — Infectious Diseases
3. RM  — Research Methodology
4. NT  — Nutrition
5. ImD — Immune Disturbances
6. PHC — Public Health Care
7. SSC — Student Selected Components

The current Modules page already opens a dedicated Module detail/overview page for each Module containing:

- introduction
- assessments / marks
- learning hours
- semester information
- final goal
- module artwork

We now need to add PDF Resources to each Module.

A Module can contain:

0, 1, 3, 10, 20, or more resources.

There is NO application-level maximum number of resources per Module.

Every resource is:

- a PDF
- has its own title
- belongs to exactly one of the seven Modules
- stored privately in Cloudflare R2
- opened using the authenticated PDF experience
- managed from Console by Admin/Owner
- visible at the bottom of that Module's detail page

Large resource PDFs may be:

100 MiB
150 MiB
up to 200 MiB

Maximum resource PDF size:

200 MiB exactly:

200 * 1024 * 1024 bytes

This large-file limit applies ONLY to Module Resources.

DO NOT raise existing limits for:

- Lecture PDF
- Notes
- AI PDF input
- any other upload feature

Those existing features must remain unchanged.

---

# 2. IMPORTANT ARCHITECTURE DECISION

DO NOT store Module Resources inside the existing Lecture `Material` model.

Current academic Material records are Lecture-scoped.

A Module Resource is NOT a Lecture Material.

Do NOT:

- create fake Lectures for Modules
- assign Module Resources to arbitrary lectureIds
- make lectureId nullable merely for this feature
- turn Material into a polymorphic model
- overload Material.type with MODULE_RESOURCE

That would couple two unrelated domains and risk Lecture/Notes/PDF regressions.

Create a dedicated model.

---

# 3. PRISMA MODEL

Add a focused model similar to:

model ModuleResource {
  id              String   @id @default(uuid())
  moduleId        String
  title           String
  storagePath     String   @unique
  fileSizeBytes   Int
  status          String   @default("READY")
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  @@index([moduleId, status, createdAt])
}

Exact fields may be refined if existing project conventions require it.

Do NOT create a Module database table merely for this feature.

The seven Modules are existing static application identities.

`moduleId` must be validated application-side against exactly:

CA
ID
RM
NT
ImD
PHC
SSC

No arbitrary module string is allowed.

# 10. LARGE FILE ARCHITECTURE

IMPORTANT.

Do NOT send a 200 MiB Module Resource through the existing:

POST /api/materials/upload

route.

Do NOT read a 200 MiB PDF into a Node Buffer.

Do NOT use:

fs.readFile(200MB)
→ Buffer
→ PutObject

inside Render.

Do NOT raise the generic Material Multer limit to 200 MiB.

Module Resources require a dedicated direct-to-R2 upload architecture.

Preferred:

Frontend
→ authenticated backend creates upload authorization
→ frontend uploads binary DIRECTLY to Cloudflare R2
→ backend verifies uploaded object
→ backend commits ModuleResource metadata
→ students access through authenticated opening flow

R2 credentials remain backend-only.

---

# 11. CLOUDLFARE R2 DIRECT UPLOAD

Reuse the existing S3-compatible R2 client.

Generate short-lived presigned upload URLs server-side.

NEVER send:

R2_ACCESS_KEY_ID
R2_SECRET_ACCESS_KEY
R2 API token

to the frontend.

The browser/client receives ONLY temporary signed URLs for its specific object/parts.

---

# 12. STORAGE PATH

Use server-generated UUIDs.

Canonical storage path:

module-resources/<moduleId>/<resourceId>.pdf

Examples:

module-resources/PHC/uuid.pdf
module-resources/NT/uuid.pdf
module-resources/CA/uuid.pdf

Never use the user's filename as the R2 object key.

This prevents:

- path traversal
- collisions
- unsafe Unicode paths
- leaking filenames into infrastructure

---

# 13. LARGE UPLOAD STRATEGY

Because these Resources commonly range from 100–200 MiB, implement a reliable upload strategy.

Preferred:

For smaller PDFs:
single presigned PUT may be used.

For large PDFs:
use R2 multipart upload.

Recommended threshold:

100 MiB

Recommended multipart part size:

16 MiB

Allowed range may be adjusted based on R2 requirements.

Do not use extremely tiny parts.

For a 200 MiB resource, expect approximately 13 parts with 16 MiB part size.

# 16. UPLOAD AUTHORIZATION

that exact R2 object key

and:

application/pdf

Recommended:

Do not create multi-day upload tokens.

---

# 17. MULTIPART UPLOAD

For files above the chosen threshold:

Backend initializes Multipart Upload in R2.

Frontend divides file using:

File.slice(...)

Frontend requests presigned UploadPart URLs.

Upload a bounded number of parts concurrently.

Recommended:

MAX_PART_UPLOAD_CONCURRENCY = 3

Do not upload 13 parts simultaneously.

Collect:

partNumber
ETag

Then submit them to the backend completion endpoint.

Backend completes multipart upload using the existing R2 client.

---

# 18. PART RETRIES

Part-level retries are acceptable because UploadPart is idempotently addressable by upload ID + part number.

Use a small bounded retry count:

maximum 2 retries per failed part.

Use exponential/backoff delay.

Do NOT repeatedly retry indefinitely.

Do NOT retry final metadata creation blindly.

---

# 19. CANCEL

On cancel:

- abort frontend requests
- backend aborts R2 multipart upload
- clean pending metadata/reservation
- UI returns to safe idle state

# 21. CLIENT-SIDE PRECHECK

Before initiating upload:

- file must exist
- file size > 0
- file size <= 200 MiB

Server/R2 post-upload validation remains mandatory.

---

# 22. SERVER PDF MAGIC VALIDATION

Do not trust:

extension
MIME
client validation

After upload finishes but BEFORE making the resource READY:

backend must verify the actual R2 object.

Use:

HEAD object

Verify:

- object exists
- actual object size > 0
- actual size <= 200 MiB
- Content-Type is application/pdf where reliable

Then use an R2 ranged GET:

bytes=0-4

Verify the first bytes equal:

%PDF-

If not:

- delete the R2 object
- do not create/activate ModuleResource
- return safe validation error

This keeps the same security principle as existing PDF uploads without downloading the full 200 MiB object into Render.
