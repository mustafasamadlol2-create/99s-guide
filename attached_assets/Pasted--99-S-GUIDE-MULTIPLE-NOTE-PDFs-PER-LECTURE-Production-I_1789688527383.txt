# 99'S GUIDE — MULTIPLE NOTE PDFs PER LECTURE
## Production Implementation — Up to 10 NOTE PDFs Per Lecture

The current production application supports generic `Material` rows related to a Lecture.

Current important behavior discovered in the repository:

- Prisma `Material` already supports multiple rows per Lecture.
- There is NO database uniqueness constraint forcing one NOTE per Lecture.
- `/api/materials/upload` currently treats PDF and NOTE the same and deletes all previous materials of the same lecture/type before creating the new material.
- Therefore uploading a second NOTE currently replaces/deletes the previous NOTE.
- Multiple existing NOTE rows are also collapsed in several frontend/read paths through `.find(...)` and the legacy singular `notesPdfUrl`.
- `LectureDetailView` currently opens only one NOTE PDF.
- Existing `DELETE /api/materials/:id` already supports deleting an individual Material.
- D1 sync already mirrors generic `Material` rows.
- R2/Supabase Storage behavior must remain private and unchanged.
- Main lecture PDF behavior must remain ONE primary PDF per lecture.
- Only NOTE PDFs are changing to multi-file behavior.

The required product behavior is:

```text
Lecture
├── PDF      → maximum 1 primary lecture PDF
├── NOTE     → maximum 10 independent PDF files
├── VIDEO
├── MCQs
└── Flashcards

Implement this as a focused production change.

Do NOT redesign unrelated parts of the app.

1. PRIMARY REQUIREMENT

A single Lecture must support:

0–10 NOTE PDF materials

Each NOTE is an independent Material row with:

unique id
title
type = "NOTE"
fileUrlOrLink
storagePath
lectureId
createdAt

Uploading a new NOTE must NOT delete or replace previous NOTE materials.

Maximum:

10 NOTE files per Lecture

The 11th NOTE must be rejected safely by the SERVER.

Frontend limits are supplementary only.

2. NO DATABASE MIGRATION

The existing Prisma schema already supports:

Lecture 1 → many Material

Do NOT change Prisma schema unless you discover an actual unavoidable constraint.

Expected:

No Prisma schema change
No migration
No new table

Do not add an array column or JSON column to Lecture.

Use existing Material rows correctly.

3. PRESERVE PRIMARY PDF BEHAVIOR

This change applies ONLY to:

type = NOTE

Existing:

type = PDF

must continue behaving exactly as it does now:

new PDF
→ replaces previous primary PDF for that Lecture
→ old Storage object removed best-effort
→ DB points to new PDF
→ D1 mirrored

Do NOT accidentally allow 10 primary lecture PDFs.

4. CHANGE NOTE UPLOAD SEMANTICS

Current /api/materials/upload contains replacement logic similar to:

find existing lecture/type materials
deleteMany({ lectureId, type })
create new Material
delete old Storage objects
sync delete old rows
sync upsert new row

That replacement behavior must remain for PDF.

For NOTE:

existing NOTE rows stay intact
new NOTE is appended

Never run:

deleteMany({ lectureId, type: "NOTE" })

during a normal NOTE upload.

Never delete previous NOTE Storage objects merely because another NOTE was uploaded.

5. AUTHORITATIVE 10-NOTE SERVER LIMIT

The backend is authoritative.

Before accepting a NOTE:

count existing NOTE materials for lecture

If count >= 10:

return a safe response such as:

HTTP 409

{
  "error": "This lecture already has the maximum of 10 notes.",
  "code": "NOTE_LIMIT_REACHED",
  "max": 10,
  "currentCount": 10,
  "remaining": 0
}

Exact wording may follow project conventions.

Frontend-only enforcement is NOT enough.

6. RACE-SAFE LIMIT

The limit must remain correct if two uploads happen at nearly the same time.

Recommended pattern:

Cheap preflight count before Storage upload.
Upload new object to Storage.
Inside an appropriate PostgreSQL transaction:
re-count NOTE rows for the Lecture
reject if already 10
create new Material otherwise
If transaction rejects because limit was reached:
delete the newly uploaded Storage object
leave all existing NOTE rows untouched

Use Serializable isolation or another existing race-safe project pattern if compatible.

If a serializable retry is used:

bounded retry only
do not retry arbitrary failures

Do not leave orphan Storage files.

7. ONE FILE PER HTTP UPLOAD MAY REMAIN

Do NOT create a huge 10 × 50 MiB multipart request unless there is a compelling reason.

Preferred production architecture:

Admin selects multiple NOTE PDFs in one UI action
→ frontend upload queue
→ existing single-file `/api/materials/upload`
→ each NOTE uploaded independently
→ max 2 concurrent uploads

This avoids:

huge 500 MiB requests
reverse-proxy timeout risk
giant memory/buffer usage
difficult partial rollback

Keep the backend route one-file-at-a-time unless repository evidence strongly favors a dedicated batch endpoint.

8. NOTE UPLOAD MUST NOT AUTO-RETRY A WRITE

Important:

A NOTE upload that succeeded on the server but lost its response must not be blindly replayed automatically.

For NOTE upload API requests use:

retries: 0

in the frontend.

Do not let generic automatic network retry create duplicate NOTE rows.

Manual retry by the administrator is acceptable.

PDF replacement behavior may retain its existing behavior unless changing it is required.

9. ADMIN NOTES UI — MULTI-FILE SELECTION

Modify UploadMaterial.tsx only as necessary.

Still retain server enforcement because another administrator may upload simultaneously.

12. NOTE FILE LIST BEFORE UPLOAD

Selected NOTE PDFs should render as a responsive list/cards showing:

readable size

remove button
upload state

Default title:

filename without .pdf

Allow admin to edit the title before upload.

Do not require manually entering one single title for all 10 files.

Each NOTE must have its own title.

13. UPLOAD QUEUE

upload only selected NOTE files
max 2 simultaneous uploads
preserve visual order

Waiting
Uploading

A small spinner/status is sufficient.

14. PARTIAL FAILURE UX

Because uploads are independent, a batch may partially succeed.

Example:

8 selected
6 uploaded
2 failed

Do NOT delete the six successfully uploaded Notes.

Show a clear summary:

6 notes uploaded successfully.
2 failed and can be retried.

Failed files may remain selected for manual retry.

Successfully uploaded files should leave the pending queue or become visibly completed.

15. NOTE DELETE / MANAGEMENT

Because the Lecture has a maximum of 10 notes, administrators must be able to free a slot.

Reuse the existing:

DELETE /api/materials/:id

Do NOT create another delete architecture.

In NOTE admin mode show the existing NOTE materials for the selected Lecture.

For each existing note show:

title
uploaded date if available
delete/remove action

Use the project's existing confirmation style before deletion.

After delete:

Storage object deleted through existing backend behavior
PostgreSQL Material deleted
D1 delete reused
cache invalidated
materials_updated emitted
note count updates without page reload

Do not add edit/rename behavior unless already easy and safe.
