# 1. PRIMARY CLOSURE GOAL

Produce the final implementation-ready local/cloud durability contract for Prompt 21.

The final design must guarantee, within normal local-storage durability limits:

1. A locally successful explicit Apply cannot be silently forgotten as an unsynchronized intent merely because the app crashes between two local writes.

2. An incomplete local Apply cannot accidentally upload a configuration that never successfully became locally committed.

3. A successful remote adoption cannot permanently leave local config and known-cloud metadata in a contradictory state after a crash.

4. A clean device gets bounded reconciliation opportunities to discover changes made on another device without introducing polling.

5. A first `empty` KV read cannot immediately establish "cloud is empty" when the client has no known cloud identity.

# 5. LOCAL CRASH-CONSISTENCY DEFECT

Prompt 20C proposed:

CONFIG KEY:

```text
99s:personalization:v1:<user>
```

and separate SYNC METADATA KEY:

```text
99s:personalization-sync:v1:<user>
```

while also saying:

the current committed config is the source for the pending upload.

This is not crash-safe by itself.

Example:

1. User presses Apply.
2. New config successfully writes to config cache.
3. Process/app crashes BEFORE `pendingIntentId` is persisted.

After restart:

- the new personalization is locally committed
- sync metadata may say there is no pending upload
- the explicit Apply may never be uploaded
- a later remote reconciliation could replace that locally applied state

This architecture is rejected.

---

# 6. OPPOSITE WRITE ORDER IS ALSO UNSAFE

Writing pending metadata FIRST is not sufficient either.

Example:

1. Pending intent/config metadata is written.
2. Local config write fails or app crashes.
3. Old local committed config remains.
4. Sync layer sees pending intent.

Without a durable association between:

intent
and
the config that actually became committed

the client can upload the wrong state.

Therefore Prompt 21 needs an explicit crash-safe local outbox model.

# 11. OUTBOX SHAPE

# 12. WHY OUTBOX DUPLICATES CONFIG

The duplication is intentional.

It protects against local two-key crash windows.

The outbox is small:

PersonalizationConfigV1 max 16 KiB.

Current actual config is far smaller.

This is preferable to silently losing explicit user intent.

---

# 13. OUTBOX IS NOT MUTATION HISTORY

V1 has exactly ONE pending personalization snapshot.

```text

→ user Applies C2

```

C1 does not need to sync first.

Having pending intent in both metadata and outbox creates another consistency problem.

# 16. APPLY — CRASH-SAFE LOCAL WRITE ORDER

For an explicit Apply:

1. Validate Draft.
2. Generate ONE new opaque `intentId`.
3. Build complete `PersonalizationOutboxV1`.
4. Persist OUTBOX first.
5. Persist the normal Phase-4 CONFIG CACHE second.
6. Only if CONFIG CACHE persistence succeeds:
   - commit Provider state locally
   - clear dirty
   - report local Apply success
7. Attempt cloud PUT asynchronously/according to connection state.

This exact ordering is intentional.

---

# 17. APPLY — OUTBOX WRITE FAILURE

If OUTBOX persistence fails:

- do NOT write the new config cache
- do NOT commit Draft
- Apply remains a local persistence failure
- existing committed config remains
- existing previous outbox, if any, must not be accidentally replaced

This preserves Phase-4 local Apply atomicity.

---

# 18. APPLY — CONFIG WRITE FAILURE AFTER OUTBOX

If:

OUTBOX write succeeds
but
CONFIG CACHE write fails

then:

- do NOT commit Provider state
- Apply is a local failure
- attempt to remove the newly created outbox best-effort

However a crash may prevent cleanup.

Therefore startup must validate outbox-to-cache correspondence before uploading.

---

# 19. ORPHAN OUTBOX VALIDATION

At account hydration:

If OUTBOX exists:

validate:

```text
outbox.config
```

against the currently persisted CONFIG CACHE.

If exact configs match:

→ outbox represents a locally committed Apply
→ it is valid pending cloud intent.

If configs do NOT match:

→ outbox is orphaned/incomplete
→ NEVER upload it
→ delete/ignore it safely
→ preserve current config cache

This closes:

outbox-written
+
config-not-written

crash window.

# 23. NEW APPLY WHILE OUTBOX EXISTS

2. Replace outbox with C2.
3. Persist config cache C2.
4. Commit C2 locally.
5. Cloud retry now represents C2 only.

If C2 local cache write fails after replacing outbox:

But this raises one more durability concern:

Prompt 20D must resolve this precisely.

---

# 24. SAFE C1 → C2 REPLACEMENT

To avoid losing C1 pending state if C2 fails locally:

the Apply implementation must not destructively replace a valid pending outbox until the new local Apply is durably complete.

Choose ONE implementation-ready strategy.

Preferred strategy:

write a TEMPORARY staged outbox key for C2:

```text
99s:personalization-outbox-staged:v1:<user>
```

then:

1. write staged C2
2. write config cache C2
3. promote staged C2 to active outbox
4. remove staged key

However this adds another local key and promotion crash states.

A simpler preferred V1 alternative is allowed:

store outbox and config in ONE atomic per-account APPLY JOURNAL record instead of separate staged keys.

Prompt 20D must compare the options and select the simplest robust architecture.

DO NOT leave C1→C2 failure semantics ambiguous.

---

# 25. PREFERRED FINAL LOCAL DURABILITY MODEL

Strong preference:

Use ONE atomic account-scoped APPLY OUTBOX/JOURNAL entry that contains:

```ts
type PersonalizationApplyJournalV1 = {
  journalVersion: 1;
  intentId: string;
  previousCommittedConfig: PersonalizationConfigV1;
  nextCommittedConfig: PersonalizationConfigV1;
  createdAt: string;
};
```

Then Apply recovery can determine whether:

- cache is previous → Apply did not complete
- cache is next → Apply completed and needs cloud sync

But this still requires safe journal replacement across C1 → C2.

Prompt 20D must choose the final model carefully.

---

# 26. ALTERNATIVE — UNIFIED LOCAL ENVELOPE V2

The other acceptable architecture is to upgrade the account-scoped local cache to ONE atomic key:

```ts
type PersonalizationLocalEnvelopeV2 = {
  cacheVersion: 2;
  savedAt: string;
  config: PersonalizationConfigV1;
  sync: {
    knownCloudRevision: string | null;
    pending: {
      intentId: string;
      config: PersonalizationConfigV1;
      createdAt: string;
    } | null;
    lastSyncState:
      | "never"
      | "clean"
      | "retryable-failure"
      | "disabled"
      | "unsupported";
    lastSuccessfulGetAt: string | null;
  };
};
```

Advantages:

- one per-account local write can atomically represent config + pending sync intent
- no two-key Apply crash window
- C1 → C2 replacement is one atomic item write
- remote-adoption config + revision can also be persisted together
- web localStorage `setItem` writes one value
- Capacitor Preferences sets one value

Cost:

- requires backward-compatible migration from cacheVersion 1
- local cache envelope changes

This may be cleaner than a multi-key journal.
