5. CURRENT GAP — ALL-DAY

The current model does NOT contain a durable all-day field.

Prompt 28 must add:

allDay Boolean @default(false)

to CalendarEvent.

Use this exact product concept.

If project naming conventions strongly require isAllDay, that is acceptable only if used consistently everywhere.

Prefer:

allDay

Do NOT infer all-day merely because a model omitted a time.

All-day must be:

explicit in source
or explicitly selected by administrator during review

Ambiguous missing-time events must remain NEEDS_REVIEW.

6. ALL-DAY STORAGE SEMANTICS

Use:

timezone = Asia/Baghdad

For an all-day event on date D:

startDateTime = D 00:00 Asia/Baghdad
endDateTime   = next calendar day 00:00 Asia/Baghdad
allDay        = true

Use half-open interval semantics.

Do NOT store:

23:59:59

as fake end-of-day when a clean next-midnight representation is possible.

Rendering must show an all-day presentation rather than 12:00 AM.

Existing non-all-day events remain unchanged.

7. EXISTING EVENTS MUST REMAIN BACKWARD COMPATIBLE

Migration requirement:

existing rows
→ allDay = false

No existing event should change its displayed date/time because of this migration.

Manual event forms must continue to work when they do not send allDay.

8. AI IMPORT PROVENANCE

Calendar events created from AI Schedule Import need durable, minimal provenance.

If repository conventions require equivalent field names:

9. IMPORT FINGERPRINT

importFingerprint exists for idempotency.

It must prevent retrying the same reviewed candidate from creating duplicate rows.

Generate the fingerprint server-side from a deterministic normalized representation containing appropriate values such as:

source SHA-256
source page
normalized local date
normalized start/end
allDay
normalized title
subject
target groups

Use a stable cryptographic hash such as SHA-256.

Do NOT trust a client-provided arbitrary fingerprint.

Server must recompute it.

10. DUPLICATE DETECTION IS BROADER THAN FINGERPRINT

Fingerprint handles retry/idempotency.

Also detect logical duplicates against:

existing manual events
existing imported events
other candidates in the same import

Use a normalized comparison involving:

date/time
title
subject where available
target-group overlap

Do NOT rely solely on source hash because the same real event may appear in another version of a schedule.

24. LARGE DOCUMENT BEHAVIOR

25. LIMITED AI CONCURRENCY

36. TIME NORMALIZATION
