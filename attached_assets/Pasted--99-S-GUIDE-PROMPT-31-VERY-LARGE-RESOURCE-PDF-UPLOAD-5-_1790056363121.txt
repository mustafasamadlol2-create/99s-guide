# 99'S GUIDE — PROMPT 31
## VERY-LARGE RESOURCE PDF UPLOAD — 5 GiB RESUMABLE DIRECT-TO-R2 MULTIPART
### FINAL RELEASE RE-CLOSURE
### SUPPORT RESOURCE PDF FILES UP TO 5 GiB
### NEVER PROXY MULTI-GIGABYTE FILES THROUGH RENDER / EXPRESS / MULTER
### DIRECT CLIENT → R2 MULTIPART DATA PLANE
### AUTHENTICATED BACKEND CONTROL PLANE
### SHORT-LIVED PRESIGNED PART URLS
### BOUNDED PART CONCURRENCY
### RETRIES + RESUME
### SERVER-SIDE FINAL SIZE / PDF SIGNATURE VALIDATION
### SAFE ABORT / ORPHAN CLEANUP
### EXISTING SMALL RESOURCE UPLOAD REMAINS BACKWARD COMPATIBLE
### AI INPUT LIMITS MUST NOT CHANGE
### PWA + CAPACITOR ARCHITECTURE AUDIT
### NO CLOUD DEPLOYMENT
### NO PRODUCTION DATABASE MIGRATION
### NO GIT COMMIT / PUSH
### DO NOT MODIFY `.agents/*`
### COMPLETE EVERYTHING BEFORE RETURNING
### DO NOT STOP FOR INTERMEDIATE PROGRESS UPDATES

Prompt 30 / 30B is CLOSED AND APPROVED.

This is the FINAL planned implementation prompt for this release cycle.

The user needs ordinary Resource PDFs to support very large files, potentially 3–5 GB.

Implement a production architecture capable of Resource PDF uploads up to:

```text
5 GiB
= 5 * 1024 * 1024 * 1024 bytes
= 5,368,709,120 bytes

This limit applies ONLY to permanent Resource PDF uploads.

DO NOT increase AI source limits to 5 GiB.

1. ABSOLUTE ARCHITECTURAL RULE

The multi-gigabyte PDF must NOT travel through:

browser
→ Express
→ Multer
→ server disk
→ R2

for the large-file path.

That architecture is forbidden.

Do NOT solve this by changing:

50 MiB → 5 GiB

inside Multer.

Do NOT solve it by:

Express timeout = 2 hours

Do NOT buffer the file in:

Node RAM
Render disk
browser RAM

as one giant object.

Required data path:

authenticated client
        ↓
backend creates secure multipart-upload session
        ↓
backend returns short-lived presigned R2 UploadPart authorization
        ↓
client slices local File into bounded parts
        ↓
client uploads parts DIRECTLY to R2
        ↓
backend lists/verifies uploaded parts
        ↓
backend completes R2 multipart upload
        ↓
backend validates final object
        ↓
backend commits Material metadata

The backend is the CONTROL PLANE.

R2 is the DATA PLANE.

2. PRESERVE EXISTING RESOURCE ARCHITECTURE

Prompt 27 verified the existing ordinary Resource PDF path:

UploadMaterial
→ authenticated backend
→ PDF validation
→ existing R2 storage abstraction
→ Material metadata
→ authenticated resource access

Keep the existing small-file path for backward compatibility where appropriate.

Recommended final behavior:

small Resource PDF
→ existing backend upload route

large Resource PDF
→ new multipart direct-to-R2 route

Use an explicit threshold.

Do not redesign unrelated lecture/material functionality.

3. LARGE RESOURCE LIMIT

Implement a maximum permanent Resource PDF size of:

5 GiB

Use bytes internally.

UI may display:

5 GB

or preferably:

5 GiB

according to existing design wording.

Files above the maximum must be rejected BEFORE multipart upload begins.

current existing bounded AI limit
NOT 5 GiB

Do not let a 5-GiB Resource file accidentally enter AI extraction/generation.

8. SESSION DURABILITY

This is a resumable multi-gigabyte upload.

The session should survive:

temporary browser network loss
backend process restart
frontend page reload where practical

Preferred implementation:

persist minimal multipart-session metadata in PostgreSQL.

Use a narrowly scoped model such as:

ResourceMultipartUpload

or repository-consistent equivalent.

Do NOT store uploaded binary parts in PostgreSQL.

Do NOT store presigned URLs.

Do NOT store R2 credentials.

R2 itself remains authoritative for uploaded parts.

Do not add an unnecessary duplicate model if the project already has an appropriate durable upload-session model.

15. MULTIPART PART SIZE

Choose a production-safe default.

Preferred:

32 MiB per part

for large Resource PDFs.

At 5 GiB this yields approximately:

160 parts

which is comfortably bounded.

Use configuration where appropriate, for example:

RESOURCE_MULTIPART_PART_SIZE_BYTES

Validate/clamp it.

Do not permit tiny part sizes that generate thousands of requests.

Do not permit absurdly huge parts that create browser-memory pressure.

16. S3/R2 MULTIPART LIMIT SAFETY

Validate the resulting expected part count.

Never exceed provider multipart limits.

Use the actual R2/S3-compatible constraints as implemented by the SDK/provider.

Do not hardcode unsupported assumptions without checking current dependencies/docs/comments already present in the project.

For the configured 5-GiB maximum, the default part plan must be safely below maximum part count.

17. PART PLAN

Implement a pure deterministic helper:

file size
+
part size
→
part numbers
byte offsets
byte lengths
expected total parts

The final part may be smaller.

No other part may be unexpectedly short at completion.

18. NO WHOLE-FILE READ IN FRONTEND

This is a hard gate.

Search final frontend source.

Forbidden for the large path:

await file.arrayBuffer()
await blob.arrayBuffer()   // on entire file
FileReader.readAsArrayBuffer(fullFile)
base64 whole file
FormData containing 5 GiB file sent to backend

Required:

file.slice(start, end)

per bounded part.

Only one bounded part per upload worker may be held at a time.

19. BOUNDED FRONTEND CONCURRENCY

Upload only a small number of parts concurrently.

Recommended default:

3

Use a configurable bounded value.

Good range:

2–4

Do not upload 160 parts simultaneously.

20. PRESIGNED PART URL API

Do NOT return 160 permanent URLs if avoidable.

Implement an endpoint that issues short-lived presigned UploadPart URLs for requested valid part numbers.

Conceptually:

POST /api/materials/uploads/multipart/:sessionId/parts

Input:

partNumbers: [...]

Limit the number of URLs returned in one request.

For example:

10–20 part URLs

per request.

21. PRESIGNED URL EXPIRY

Use short-lived UploadPart URLs.

Preferred conceptual TTL:

10–20 minutes

for each signed URL.

If a URL expires during a long upload:

client requests a fresh URL for that same unfinished part.

Do not force restart of the entire upload.

22. PRESIGNED URL SECURITY

Every signed URL must be scoped to:

exact bucket
exact object key
exact uploadId
exact part number

The client must not be able to change the object key or upload ID through request parameters.

Server loads them from its session.

23. CLIENT CREDENTIALS

The frontend must NEVER receive:

R2 access key
R2 secret key
AWS secret
Cloudflare token
service credentials

Presigned URLs only.

24. DIRECT PART UPLOAD

Web/PWA upload:

File.slice()
→ PUT presigned part URL

Use a mechanism that supports upload progress.

XHR is acceptable if it fits current architecture.

Fetch is acceptable if current runtime provides useful upload behavior, but do not fake progress.

Capture successful completion.

Do not keep the whole file in memory.

25. PART RETRY

A single part may retry on transient failures such as:

network interruption
408
429
500
502
503
504

Use bounded retry/backoff.

Do NOT retry indefinitely.

Suggested:

maximum 4–5 attempts per part

with bounded exponential backoff/jitter.

26. EXPIRED PRESIGNED URL

If an upload part fails because the signed URL expired:

request new URL
→ retry same part

Do not recreate the entire multipart upload.

Do not reupload completed parts.

27. PART PROGRESS

Track:

uploaded bytes
total bytes
completed parts
total parts
current throughput if safely measurable

UI should show real progress.

Do not fake progress.

28. UPLOAD SPEED

Avoid recalculating SHA-256 for the entire 5-GiB file in JavaScript before upload.

That would add a huge blocking read.

Do not require a full-file client hash as a prerequisite.

If integrity metadata is needed:

use provider/server metadata and final validation.

Optional per-part checksums may be used only if they do not cause a full-file pre-read.

29. SERVER MUST NOT TRUST CLIENT ETAGS

At completion, prefer the backend to obtain authoritative uploaded-part state from R2.

Use:

ListParts

for the multipart upload.

Build the completion list from R2-reported:

PartNumber
ETag
Size

rather than blindly trusting an arbitrary client-provided ETag array.

31. RESUME USES R2 AS AUTHORITY

When determining completed parts:

query:

ListParts

or equivalent authoritative provider state.

Do not rely only on browser localStorage saying a part completed.

32. PAGE-RELOAD RESUME

Where practical support:

start upload
→ page closes/reloads
→ UI remembers safe session id/metadata
→ administrator reselects the SAME file
→ client validates file identity metadata
→ server lists uploaded parts
→ only missing parts upload

Do not persist multi-gigabyte file bytes in IndexedDB.

33. FILE RESELECTION SAFETY

Before resuming against an existing multipart session verify at minimum:

filename
size
MIME

and any safe available local metadata such as:

lastModified

If selected file differs:

do not upload it into the old session.

Require a new session or explicit restart.

34. BACKEND RESTART RESUME

If using persisted session metadata:

a backend restart must NOT make an active R2 multipart upload unrecoverable.

The user should be able to:

resume status
→ receive completed parts from R2
→ continue missing parts

until session expiry.

35. COMPLETION ENDPOINT

Implement:

POST /api/materials/uploads/multipart/:sessionId/complete

or equivalent.

The client should NOT supply arbitrary Material database data at this stage beyond fields already bound to the server session.

36. COMPLETION VALIDATION — PART COUNT

Before CompleteMultipartUpload:

server calls R2 ListParts.

Verify:

part numbers contiguous
1…expectedPartCount

No missing part.

No duplicate part.

No out-of-range part.

37. COMPLETION VALIDATION — PART SIZES

Verify provider-reported uploaded sizes.

For each non-final part:

size == expected configured part size

For final part:

size == exact remaining bytes

Total:

sum(parts) == declared file size

If mismatch:

do not create Material metadata.

38. COMPLETE MULTIPART

Only after validation:

CompleteMultipartUpload

using authoritative provider ETags.

Then:

HeadObject

and verify final ContentLength.

Expected:

ContentLength == declared size
39. FINAL PDF SIGNATURE VALIDATION

Direct-to-R2 upload bypasses the old Multer binary validator.

Therefore validation MUST be restored AFTER object completion and BEFORE Material metadata becomes usable.

Use a bounded R2 range request such as the first:

1 KiB

or repository-appropriate amount.

Verify the current accepted PDF signature rules.

Do NOT download the entire 5-GiB object through Render.

40. PDF HEADER

Use existing trusted PDF signature validation if possible.

A valid PDF must contain the expected PDF header according to the existing product validation contract.

If signature validation fails:

delete completed object
mark session FAILED/ABORTED
create zero Material rows

Do not leave malicious/non-PDF content accessible as a Resource.

41. FINAL MIME

Do not trust only browser-declared MIME.

Combine:

declared MIME
extension
binary signature

according to existing Resource rules.

Final product remains PDF-only.

Do NOT add Resource images.

42. MATERIAL METADATA COMMIT

Only after:

multipart complete
+
size verified
+
PDF signature verified

Use existing Material creation/storage URL semantics.

Do not create a parallel Resource database model.

43. DATABASE TRANSACTION / CLEANUP

If Material DB creation fails AFTER R2 multipart completion:

attempt to delete the completed R2 object.

Do not leave a permanent orphan intentionally.

If deletion fails:

log safe orphan-cleanup metadata for later reconciliation.

Do not tell the user upload succeeded.

44. IDEMPOTENT COMPLETE

Calling complete twice must not create two Material rows.

Use server session state and/or a unique association so:

first complete
→ Material created

second complete
→ return existing completion result

not duplicate metadata.

45. ABORT ENDPOINT

Implement:

DELETE /api/materials/uploads/multipart/:sessionId

or equivalent.

Required behavior:

authorization
→ AbortMultipartUpload if active
→ mark session ABORTED
→ remove lightweight resume state

If object was already completed but Material commit failed and cleanup is required:
delete the object safely.

46. ABANDONED UPLOAD CLEANUP

A 5-GiB multipart system must not accumulate incomplete uploads forever.

Implement a bounded cleanup mechanism.

Options:

persisted session expiry + opportunistic cleanup
scheduled application cleanup if current architecture supports it
R2 lifecycle rule as an external deployment requirement
a combination

Do NOT invent background infrastructure requiring a new service.

Preferred application session TTL:

24 hours

or similarly reasonable value.

47. R2 MULTIPART LIFECYCLE RULE

Audit whether bucket lifecycle configuration for aborting incomplete multipart uploads exists.

Do NOT modify live Cloudflare configuration.

If a lifecycle rule is needed, report the exact required deployment action.

The application must still have safe abort/session handling.

48. SESSION EXPIRY

can be safely aborted/cleaned

User can restart with a fresh session.

49. ADMIN AUTHORIZATION

50. OWNER ISOLATION

51. LECTURE AUTHORIZATION

52. RATE LIMITS

Use reasonable endpoint-level limits.

Do not rate-limit direct R2 PUT bytes through Express because the bytes do not pass through Express.

53. ACTIVE SESSION LIMIT

Use a reasonable active-session limit, such as:

3–5 active large uploads per admin

according to current product expectations.

Report exact final value.
