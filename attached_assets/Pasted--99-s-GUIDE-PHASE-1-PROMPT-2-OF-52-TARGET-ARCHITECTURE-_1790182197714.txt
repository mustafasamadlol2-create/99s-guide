# 1. CRITICAL ARCHITECTURAL CORRECTION

The following architecture is mandatory.

The future systems must NOT become a completely separate Cloudflare-only application database.

## Canonical data model

The existing:

**Supabase PostgreSQL + Prisma**

remains the canonical relational database.

New feature entities must be represented cleanly in the existing Prisma/PostgreSQL relational model when durable authoritative state is required.

This means future feature tables/models such as Focus, Points, Achievements, Mastery, Recall, etc. will ultimately have canonical relational representation in PostgreSQL/Supabase.

However:

# NORMAL HIGH-FREQUENCY RUNTIME ACCESS SHOULD AVOID HITTING SUPABASE DIRECTLY WHENEVER PRACTICAL.

The intended architecture is:

```text
Canonical Supabase/PostgreSQL
        │
        │ authoritative write / durable relationship
        │
        ▼
Cloudflare synchronization / projection layer
        │
        ├── D1
        ├── KV
        ├── Analytics Engine
        ├── Durable Objects
        ├── R2
        ├── Queues
        └── Workers
        │
        ▼
High-frequency application runtime
```

Do NOT interpret this as:

```text
Supabase abandoned
```

and do NOT interpret it as:

```text
Every click reads/writes Supabase.
```

The goal is:

**Supabase = canonical durable relational truth.**

**Cloudflare = operational/runtime/cache/realtime/analytics layer wherever technically appropriate.**
