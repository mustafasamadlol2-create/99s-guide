# 99’s GUIDE — PROMPT 13 VERIFICATION GATE

## REAL POSTGRESQL GROUP FOCUS VALIDATION

### CAPACITY + INVITES + AUTHORIZATION + IDEMPOTENCY + MIGRATION REPLAY

### DOES NOT COUNT AS A NEW PROMPT IN THE 52-PROMPT ROADMAP

Prompt 13 implementation is provisionally accepted.

Do NOT begin Prompt 14 yet.

The remaining gate exists because Prompt 13 introduced:

* two new canonical PostgreSQL models;
* transactional room/membership behavior;
* race-sensitive capacity enforcement;
* private invitation security;
* host/member authorization;
* canonical authorization context that Prompt 14 will trust when issuing Worker capabilities.

These properties must be proven against real PostgreSQL before capability issuance is built on top of them.

---

# 1. PRIMARY OBJECTIVE

Verify the existing Prompt 13 implementation against a safe disposable PostgreSQL schema.

This gate should require **zero production-feature changes** unless testing exposes a genuine defect.

The target outcome is:

```text
repository migrations
→ fresh isolated PostgreSQL schema
→ Group Focus room/membership tests
→ concurrency/security invariants pass
→ disposable schema removed
→ Prompt 14 gate PASS
```

7. set required test opt-in markers only for the test process;
8. run tests;
9. remove the disposable schema.

Never persist connection secrets.

# 8. HOST INVARIANT REVIEW

Prompt 13 intentionally does not use a PostgreSQL partial unique index for:

```text
one HOST membership per room
```

because Prisma 5.22 does not model that cleanly.

This is acceptable only if all production membership-role writes are server-owned and cannot create an extra Host.

Verify by code inspection and tests:

* no API accepts membership role;
* join always assigns MEMBER;
* rejoin does not alter role;
* Lecture update does not alter role;
* remove does not alter role;
* Host membership is created only during Room creation;
* no generic membership update route exists.

Add a focused contract test if missing.

Do NOT add a speculative partial unique index in this verification gate unless testing exposes a real correctness requirement that cannot be safely enforced otherwise.
