
---

# 1. PRIMARY OBJECTIVE

Create an append-only, server-authoritative Study Points ledger that future deterministic award logic can safely use.

It must provide:

1. immutable accounting entries;
2. idempotency;
3. explicit source/reason;
4. rule-version metadata;
5. positive awards and negative reversals/corrections;
6. safe balance derivation;
7. compatibility with existing legacy `PointsLog`;
8. no retroactive double counting;
9. no client authority;
10. no new reward behavior yet.

---

# 2. CRITICAL ACCOUNTING PRINCIPLE

Study Points must behave like a ledger.

Do NOT model future Points as:

```text
user.points += 10
```

without an immutable accounting entry.

Canonical rule:

```text
balance
=
sum(canonical ledger entries)
```

subject to future reconciliation/snapshot optimizations.

---

# 3. SERVER AUTHORITY

The frontend must never decide:

```text
how many Points
why Points are awarded
whether the action qualifies
which rule version applies
```

The backend owns all of those decisions.

Prompt 19 does not yet implement those decisions.

---

# 4. APPEND-ONLY

Normal application flows must never mutate the semantic value of an existing ledger entry.

Do NOT support normal:

```text
UPDATE points amount
UPDATE reason
DELETE ledger entry
```

Corrections use a new ledger row.

---

# 5. REVERSALS

If a previously applied Points entry must later be corrected, create a new negative ledger entry linked to the original.

Example:

```text
+20 original award
-20 reversal
```

Do not edit the +20 row.

---

# 6. NO AUTOMATIC NEGATIVE PUNISHMENT

Prompt 19 supports negative amounts structurally for:

```text

correction
administrative accounting repair
```

It does NOT implement:

```text
automatic punishment
integrity penalty
disciplinary deduction
```

Prompt 18 Integrity Signals do not directly subtract Points.
