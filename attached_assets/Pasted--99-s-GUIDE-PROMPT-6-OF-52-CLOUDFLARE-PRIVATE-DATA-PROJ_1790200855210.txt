# 1. FIXED ARCHITECTURE

The architecture remains:

```text
Supabase PostgreSQL / Prisma
        ↓
canonical durable truth
        ↓
atomic canonical mutation + outbox
        ↓
private-data synchronization
        ↓
Cloudflare D1 read projections
        ↓
high-frequency application reads
```

Rules:

* PostgreSQL remains canonical.
* D1 remains non-authoritative.
* D1 never overwrites PostgreSQL.
* Every D1 entity references canonical IDs.
* Stale D1 revisions must not overwrite newer ones.
* PostgreSQL fallback remains available.
* Feature flags remain disabled.
* No feature becomes visible to users after Prompt 6.

# 2. IMPORTANT COST / DUPLICATION RULE

Do NOT mirror the entire Study Engine database into D1.

Especially:

# DO NOT COPY THE RAW `StudyEvent` TABLE INTO D1.

`StudyEvent` may become one of the highest-volume PostgreSQL tables.

Copying every raw event into both PostgreSQL and D1 would:

* duplicate storage;
* duplicate writes;
* consume free-tier D1 operations;
* provide little value for normal dashboard reads.

Instead:

```text
Raw StudyEvent
    → PostgreSQL canonical only
    → later aggregation/analytics
    → StudyDailyMetric / derived projections
    → D1
```

Analytics Engine may later receive suitable aggregate telemetry.

Prompt 6 must not create a raw Study Event D1 table.

# 7. FOCUS PLAN D1 PROJECTION DESIGN

The D1 projection must optimize the normal runtime operation:

> Open Focus Hub and load the student's Focus Plans without hitting PostgreSQL.

Do NOT blindly copy the normalized PostgreSQL structure.

D1 is a read projection.

Evaluate the existing private Worker conventions and choose one of:

### Option A — separate plan/item projection tables

```text
study_focus_plans
study_focus_plan_items
```

or:

### Option B — denormalized plan projection

```text
study_focus_plans
  + bounded items_json
```

The preferred design should minimize:

* unnecessary D1 row reads;
* multiple network round-trips;
* projection complexity;
* free-tier usage.

However:

* do not store unbounded JSON;
* do not make plan items impossible to update efficiently;
* preserve canonical IDs for plan and items.

Choose based on actual D1 patterns already in the repository.

Document the decision.

# 16. REVISION SEMANTICS

Reuse the existing private-data revision mechanism where possible.

Required behavior:

```text
incoming revision > stored revision
→ apply

incoming revision == stored revision + same payload
→ idempotent success

incoming revision == stored revision + different payload
→ conflict/log/reject

incoming revision < stored revision
→ reject as stale
```

Do not let out-of-order sync resurrect stale state.

---
