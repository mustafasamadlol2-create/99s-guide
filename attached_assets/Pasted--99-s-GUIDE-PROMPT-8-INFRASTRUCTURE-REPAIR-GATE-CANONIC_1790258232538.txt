# 9. CRITICAL — REVISION CONTRACT

The previous implementation currently obtains revision using an explicit:

```text
nextval(...)
```

while also relying on a database-generated outbox `id`.

That contract is undocumented and may consume the sequence twice per row.

Fix this ambiguity.

The final implementation must have:

# ONE EXPLICITLY DOCUMENTED MONOTONIC PROJECTION REVISION SOURCE.

Choose the safest implementation after inspecting existing code.

Acceptable architectures include:

## Option A — Outbox row ID is the revision

```text
id = database-generated BIGINT
revision = same logical value as id
```

provided insertion can obtain/use one sequence value without unsafe double consumption.

## Option B — Dedicated PostgreSQL revision sequence

```text
id = database-generated BIGINT
revision = next value from dedicated monotonic BIGINT sequence
```

provided it is reproducible in migrations.

Either is acceptable.

The following is NOT acceptable:

```text
call nextval(id_sequence) manually
+
omit id
+
allow id default to call nextval(id_sequence) again
+
assume this undocumented behavior is fine
```

# 10. REVISION REQUIREMENTS

Whatever strategy is chosen:

* every outbox projection mutation gets a monotonic PostgreSQL integer revision;
