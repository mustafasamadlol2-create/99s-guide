# 1. PRIMARY OBJECTIVE

Implement a deterministic, server-authoritative pipeline:

```text
verified domain action
        ↓
Study Event validation
        ↓
idempotency validation
        ↓
PostgreSQL transaction
        ├── StudyEvent
        ├── StudyDailyMetric update where applicable
        └── D1 projection outbox for changed daily metric
        ↓
commit
```

Important:

# RAW STUDY EVENTS REMAIN POSTGRESQL-ONLY.

Do NOT mirror raw `StudyEvent` rows to D1.

Only derived/read-optimized state such as `StudyDailyMetric` is projected.

---

# 2. SECURITY MODEL

Do NOT build a generic endpoint such as:

```text
POST /api/study-events
```

that accepts arbitrary event types from the browser.

The client must never be able to say:

```json
{
  "eventType": "focus_session_completed",
  "activeSeconds": 7200
}
```

and have the server trust it.

Study Events are produced by verified domain services.

Future examples:

```text
MCQ endpoint grades answer
→ server emits mcq_attempted

Focus Service validates completion
→ server emits focus_session_completed

Recall Service validates presentation token
→ server emits spaced_recall_answered
```

Prompt 8 builds that internal engine.

No new browser-facing generic ingestion endpoint is required.

# 24. IDEMPOTENCY — CRITICAL

Canonical constraint already exists:

```text
StudyEvent(userId, idempotencyKey)
```

Implement robust behavior.

### First request

```text
FIRST_SEEN
```

Create event and metric effect.

### Replay — same key, same semantic payload

```text
REPLAY_SAME_PAYLOAD
```

Return the existing event.

Do NOT update metric again.

### Replay — same key, different semantic payload

```text
CONFLICTING_PAYLOAD
```

Reject.

Do NOT create event.

Do NOT update metric.

Do NOT award anything.

Later Integrity system may flag this.

# 25. CONCURRENT DUPLICATE SAFETY

Handle this race:

```text
request A
request B
same user
same idempotency key
```

The unique DB constraint must be the final authority.

Implementation should safely handle Prisma unique violations.

Expected:

* one canonical event;
* one Daily Metric increment;
* second request resolves as same replay or conflict;
* no double counting.

Add an appropriate test.
