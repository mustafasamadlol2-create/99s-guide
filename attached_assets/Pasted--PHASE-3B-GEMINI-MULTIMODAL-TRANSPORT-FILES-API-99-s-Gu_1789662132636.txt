# 2. CURRENT OFFICIAL PROVIDER CONSTRAINTS

Design against the current Gemini API behavior.

Current relevant constraints:

* PDF maximum: **50 MB**
* PDF maximum pages: **1000**
* Files API uploads persist temporarily for up to **48 hours**
* Files API files can be deleted explicitly
* Files may enter:

  * `PROCESSING`
  * `ACTIVE`
  * `FAILED`
* A file in `PROCESSING` must not be used for inference
* `ACTIVE` means it is available for inference
* Inline media is appropriate for smaller request payloads
* Files API is appropriate for larger media and reusable media
* Gemini supports media through inline data and file references
* `gemini-3.8-flash` remains the configured model

Do not loosen Phase 3A's stricter application limits merely because the provider permits more.

# 3. APPROVED INITIAL TRANSPORT POLICY

Use the following production policy.

## Text

Always:

```text
inline text
```

Never upload pasted text through Files API.

---

## PDF

For the initial implementation:

```text
PDF → Gemini Files API
```

Use Files API for PDFs by default.

Reasons:

* PDFs can be large
* avoids large base64 payloads
* avoids duplicating large buffers
* lecture documents naturally fit file-oriented processing
* Gemini Files API is temporary
* uploaded provider files can be explicitly deleted

Do NOT permanently store Gemini File URIs.

Do NOT treat Files API as application storage.

---

## Images

Use a hybrid strategy.

### Small image request

Use inline media when the total raw image bytes are within a conservative configured threshold.

Approved default:

```text
10 MiB total raw image bytes
```

This is an APPLICATION threshold, not a claim about Gemini's absolute provider maximum.

### Larger image request

If total raw image size exceeds the inline threshold:

```text
Images → Gemini Files API
```

This includes multi-image batches whose combined size becomes large.

# 11. FILE STATUS POLLING

After Files API upload, handle status safely.

Support:

```text
PROCESSING
ACTIVE
FAILED
```

If immediately `ACTIVE`:

continue.

If `PROCESSING`:

poll using `files.get()`.

Do NOT create an infinite loop.

Polling must respect:

* processing timeout
* outer provider timeout
* abort signal

If state becomes:

```text
FAILED
```

raise a safe provider/media error.

---

# 12. UNKNOWN FILE STATES

Do not blindly loop forever on unknown/undefined states.

Handle unknown states conservatively.

Either:

* poll within a bounded grace period if documented/appropriate
* or raise a typed provider-media error

Document your choice.

# 13. PROVIDER FILE CLEANUP

Every file uploaded to Gemini Files API should be explicitly deleted after the AI operation.

Use:

```text
files.delete(...)
```

in a guaranteed cleanup lifecycle.

Conceptually:

```ts
const uploaded = await upload(...);

try {
  return await generate(...);
} finally {
  await deleteUploadedFile(...);
}
```

For multiple provider files:

delete every successfully uploaded file.

---

# 14. PARTIAL UPLOAD FAILURE

Example:

# 15. FILES API RETENTION IS FALLBACK ONLY

Gemini Files API automatically expires uploaded files after approximately 48 hours.

This is a fallback safety net.

It is NOT the intended cleanup strategy.

The application should explicitly delete provider-uploaded media whenever possible.

# 16. CLEANUP FAILURE POLICY

If generation succeeds but Gemini file deletion fails:

Do NOT throw away a valid AI result solely because cleanup failed.

Instead:

* retain successful validated generation result
* record safe internal cleanup diagnostics
* optionally expose a sanitized provider cleanup warning in metadata
* never expose API credentials
* never expose local filesystem paths

The provider file will still expire automatically.

If generation itself failed:

the generation failure remains the primary error.

Cleanup should still be attempted.
