# 8. MCQ CANDIDATE MODEL

Phase 2 created a strict import-oriented MCQ draft.

Phase 4 needs a review-oriented candidate model because extraction can legitimately encounter incomplete source MCQs.

Create a normalized candidate contract conceptually similar to:

```ts
interface AIMCQCandidate {
  candidateId: string;

  question: string;

  optionA: string;
  optionB: string;
  optionC: string;
  optionD: string;

  correctAnswer: "A" | "B" | "C" | "D" | null;

  hint: string | null;
  explanation: string | null;

  difficulty: ExistingDifficulty | null;

  provenance: "extracted" | "generated" | "enhanced";

  source: MCQSourceEvidence | null;

  confidence: number;
  needsReview: boolean;

  warnings: string[];
}
```

Adapt this to the existing contracts.

Important:

`correctAnswer` MAY be `null` for an extracted candidate when the source does not explicitly establish the answer.

That candidate is reviewable but NOT import-ready.

# 12. CONFIDENCE SEMANTICS

Do not use confidence as a universal claim that an MCQ is medically correct.

Define the meaning per operation.

## Extract

Confidence means:

> Confidence that the application correctly identified/transcribed the MCQ structure and mapped information from the source.

It does NOT mean:

> Confidence that the source's medical answer itself is factually correct.

---

## Generate

Confidence means:

> Confidence that the generated MCQ and answer are adequately supported by the supplied educational source.

---

## Enhance

Confidence means:

> Confidence that the generated hint/explanation is consistent with the supplied MCQ and its stated correct answer.

Document this clearly.

* explanation

---

# 48. ENHANCE MUST BE TWO-STAGE

Implement Enhance mode as a controlled two-stage workflow.

## Stage 1

Run the existing extraction engine.

Result:

```text

```

## Stage 2

Send only eligible structured candidates to a dedicated enhancement request.

This second request generates ONLY the requested enhancement fields.

Do NOT ask the second model response to return rewritten questions/options.

This design is mandatory.

---

# 49. WHY TWO-STAGE ENHANCEMENT IS REQUIRED

We need deterministic protection against unwanted rewriting.

Therefore the Stage 2 provider schema must NOT even contain fields such as:

* question
* optionA
* optionB
* optionC
* optionD
* correctAnswer

as writable output.

Instead use a shape conceptually like:

```ts
interface MCQEnhancementOutput {
  candidateId: string;
  hint?: string | null;
  explanation?: string | null;
  confidence: number;
  uncertainties: string[];
}
```

The application merges the permitted fields onto the Stage 1 candidates.

Thus Gemini cannot replace the original MCQ structure through the response schema.

---

* question

* explicit correct answer
