# 3. IMPORTANT SEMANTIC RULE

For this application:

```text
clinicalConcept
```

is effectively the **front / prompt / concept side** of the flashcard.

```text
explanation
```

is effectively the **back / answer / explanatory side**.

Therefore `explanation` is not merely optional decorative metadata.

It is the canonical back side of the existing Flashcard model.

A generated Flashcard should normally contain BOTH.

Do not design generated cards with an empty back side.

# 13. CONFIDENCE SEMANTICS

Define confidence differently by operation.

## Extract

Confidence means:

> Confidence that the engine correctly identified and transcribed the Flashcard front/back structure from the supplied source.

It does NOT claim the medical content itself is factually correct.

## Generate

Confidence means:

> Confidence that the generated card is adequately supported by the supplied educational source.

## Enhance

Confidence means:

> Confidence that the newly generated back/explanation is consistent with the supplied front and source context.

Document these semantics clearly.

---

# 14. CONFIDENCE RANGE

Strictly:

```text
0.0–1.0
```

Reject:

* strings
* NaN
* Infinity
* negative values
* values >1

# 21. SUPPORTED EXTRACTION STRUCTURES

```text
Question → Answer
Front → Back

```

# 22. EXTRACTION PRESERVATION

Preserve:

* front wording
* back wording
* source order
* language
* medical terminology

* improve grammar

* expand answers
* generate missing facts
* rewrite the card
* convert it into a different study format

---

# 23. FRONT-ONLY CARDS

If the source clearly contains a card front/concept but no explicit back/answer:

preserve:

```text
clinicalConcept = extracted front
explanation = null
```

Do NOT answer it using Gemini's medical knowledge.

Mark it:

```text
importReady = false
needsReview = true
```

Enhance mode can later fill the missing explanation.

---

# 24. BACK WITHOUT FRONT

If a source item cannot reliably identify the front/concept:

do not invent one.

Report the source item as skipped.

---

# 25. EXTRACTION DOES NOT ENHANCE

If source answer is:

```text
Protein A
```

extract:

```text
Protein A
```

Do not automatically rewrite it as a paragraph explaining Protein A.

Enhancement and generation are separate operations.

---

# 26. UNSUPPORTED SOURCE ITEMS

Report source material that cannot safely map to the existing Flashcard model.

Examples:

* complex multi-column matching exercise
* malformed card
* unreadable content
* image with insufficient readable content
* multi-answer structure that cannot map cleanly to one front/back pair
* content that is clearly not a Flashcard

Use structured skipped-item reporting.

# 33. ONE LEARNING POINT PER CARD

Prefer atomic cards.


---

# 34. FRONT QUALITY

Generated `clinicalConcept` should generally be:

* concise
* clear
* independently understandable
* specific enough to have one meaningful back
* not excessively vague

Avoid:

```text

Important?
```

---

# 35. BACK QUALITY

Generated `explanation` should:

* answer the front directly
* be concise but educational
* contain the key information needed for recall
* remain source-grounded
* avoid unnecessary textbook-length paragraphs

Do not make every card several paragraphs long.

---

# 36. NO FRONT/BACK DUPLICATION

A card where the back merely repeats the front is low quality.

Example:

```text
Front: What is Protein A?
Back: Protein A.
```

should be flagged unless that structure is genuinely meaningful in context.

Add a conservative quality check for near-identical front/back content.

# 42. MODE 3 — ENHANCE EXISTING FLASHCARDS

Enhancement is intended primarily for existing Flashcard-like sources where:

```text
clinicalConcept
```

```text
explanation
```

This is especially useful for:

* term lists
* front-only cards
* question lists intended to become Anki cards

---

# 43. IMPORTANT ENHANCEMENT POLICY

The initial Phase 5 enhancement policy is:

**fill missing explanation/back only.**

Do NOT rewrite an existing non-empty explanation.

Do NOT rewrite the front.

Do NOT create an “improve existing explanation” mode yet.

That can be a future explicit feature if desired.

---

# 44. ENHANCEMENT MUST BE TWO-STAGE

Use the same strong architecture as MCQ enhancement.

## Stage 1

Run Flashcard extraction.

Result:

```text
structured Flashcard candidates
```

## Stage 2

Select only cards where:

```text
clinicalConcept exists
AND
explanation is missing
```

Send these candidates to a dedicated enhancement request.

---

# 45. STAGE 2 OUTPUT MUST BE MINIMAL

The provider Stage 2 schema should contain only fields the model is allowed to create.

Conceptually:

```ts
interface FlashcardEnhancementOutput {
  candidateId: string;
  explanation: string;
  confidence: number;
  uncertainties: string[];
  source?: FlashcardSourceEvidence | null;
}
```

Do NOT allow Stage 2 to output writable:

```text
clinicalConcept
```

Thus it cannot rewrite the original front through the response schema.
