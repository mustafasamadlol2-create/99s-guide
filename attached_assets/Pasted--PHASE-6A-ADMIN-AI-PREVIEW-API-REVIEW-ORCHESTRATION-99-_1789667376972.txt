# 15. LARGE BINARY INTAKE MUST BE DISK-BACKED

This is important.

Do NOT use unbounded or large-file:

```text
multer.memoryStorage()
```

for PDF and image batches.

PDF may reach 50 MiB.

Multi-image requests may be substantially larger.

Use a disk-backed, request-scoped temporary intake path/capability.

It must:

* use random generated names
* never use raw filenames as paths
* live under a dedicated AI temp area
* never use the production Lecture upload folder
* never write R2
* be cleaned on every path

---

# 16. REUSE PHASE 3A CAPABILITY SAFETY

Phase 3B introduced trusted runtime-branded staged-file capabilities.

Preserve this security model.

The HTTP upload layer must NOT introduce:

```text
arbitraryPath: string
```

as a valid AI source.

If needed, extend Phase 3A narrowly so the HTTP intake layer can hand off a trusted uploaded-file capability.

Acceptable conceptual flow:

```text
multipart stream
→ AI-controlled temporary file
→ trusted capability
→ AIInputService validation/normalization
```

Do not expose arbitrary filesystem paths through public contracts.

---

# 17. AVOID DOUBLE-STAGING LARGE FILES

Where practical, avoid:

```text
HTTP temp copy
→ full read
→ second complete temp copy
```

for a 50 MiB PDF.

Prefer a secure adoption/streaming/capability approach.

However:

Security and correctness are more important than premature optimization.

If one controlled additional move/rename is required, explain it.

Do not keep multiple large buffers in memory.

---

# 18. HTTP BINARY LIMITS

Phase 3A remains the content hard boundary:

* PDF: 50 MiB
* Image: 20 MiB each
* Images: up to 20

Additionally establish a route-level maximum **total image batch size**.

Recommended initial value:

```text
100 MiB total image request
```

Reason:

20 × 20 MiB = 400 MiB theoretical Phase 3A maximum, which is unnecessarily large for one synchronous admin HTTP request.

Use the lower of:

* per-file rules
* total HTTP request safety rule

Centralize the value.

Do not change the underlying Phase 3A per-image semantics.

---

# 19. TEXT LIMIT

# 32. CLIENT DISCONNECT

Tie the HTTP request lifecycle to cancellation.

If the admin:

* closes the browser
* navigates away
* cancels the request
* loses connection

the backend should abort provider work when safely possible.

Use:

```text
AbortController
```

or the existing provider signal design.

Do not leave Gemini generation running unnecessarily after the client is gone.

---

# 33. ABORT EVENT SAFETY

Use the correct Express/Node lifecycle events.

Do not accidentally abort a valid request simply because the request body completed.

Distinguish:

* request upload completion
* response/socket close before completion

Clean listeners afterward.

Test the chosen behavior.

# 34. AI CONCURRENCY PROTECTION

Because the feature uses a limited AI provider quota, add lightweight server-side concurrency protection.

Recommended initial default:

```text
1 active AI preview per authenticated admin
3 active AI previews globally per Node process
```

This protects against:

* repeated clicks
* multiple browser tabs
* accidental free-tier exhaustion
* excessive simultaneous 50 MiB processing

Make limits centralized/configurable.

Do not add Redis.
