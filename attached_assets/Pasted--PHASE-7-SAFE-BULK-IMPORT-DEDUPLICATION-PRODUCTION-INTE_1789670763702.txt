# 20. DUPLICATE NORMALIZATION

Create a shared conservative normalization utility.

At minimum:

* Unicode normalization
* trim
* collapse repeated whitespace
* normalize harmless spacing around punctuation where safe

* aggressively stem medical terms

---

# 21. EXACT DUPLICATE

An exact duplicate means normalized duplicate key is equal.

Example:

```text
"What is Protein A?"
"What   is Protein A? "
```

should be exact duplicates after normalization.

---

# 22. POSSIBLE / NEAR DUPLICATE

Also detect conservative near duplicates.

Goal:

catch examples such as:

```text
What is the main virulence factor of S. aureus?
What is the major virulence factor of Staphylococcus aureus?
```

without classifying broadly related questions as duplicates.

Use a deterministic, testable string-similarity method.

Recommended:

* normalized character n-gram similarity
* Dice/Jaccard-style comparison

or another focused dependency-free approach.

Do NOT use Gemini for duplicate detection.

Do NOT add embeddings/vector DB.

---

# 23. NEAR-DUPLICATE THRESHOLD

Centralize a conservative threshold.

Recommended starting point:

```text
0.92
```

Do not compare extremely short strings with fuzzy similarity.

Use a minimum normalized length before near-duplicate classification.

Example:

```text
20 characters
```

Exact duplicates remain detectable regardless of length.

# 27. DUPLICATE POLICY

For the initial safe import implementation:

**Both exact and possible duplicates are skipped by default during commit.**

Do not automatically insert a possible duplicate.

This follows the safety-first approved product direction.

The frontend can retain skipped candidates after import so the administrator sees what was not imported.

Do not add an override flow in Phase 7 unless the existing UX makes it exceptionally simple and safe.

---

# 28. NO SILENT DUPLICATE DELETION

Duplicate candidates are not erased from frontend review history.

After commit:

* new candidates become imported
* duplicate candidates remain visible as skipped duplicates

The admin must understand what happened.

---

# 29. COMMIT MUST RECHECK DUPLICATES

The final `/import` endpoint:

1. validates request
2. validates Lecture
3. queries existing relevant records
4. performs duplicate analysis again
5. determines final insert set
6. inserts only final `new` candidates

Do not trust duplicate statuses sent by frontend.

Ideally frontend should not send statuses at all.

---

# 30. TRANSACTIONAL IMPORT

All final PostgreSQL inserts for one import request must be atomic.

MCQ example:

```text
94 new MCQs
→ one bounded transaction
```

Flashcards equivalent.

Do NOT send:

```text
94 independent create requests
```

Do NOT perform one transaction per candidate.

---

# 31. ALL-OR-NOTHING FOR NEW ITEMS

If PostgreSQL insertion fails:

```text
0 of the final new items
```

should remain inserted from that transaction.

Duplicates skipped before insertion are not considered failures.

# 34. TRANSACTION ISOLATION / RACE SAFETY

Duplicate detection must be as race-safe as practical.

Perform the final existing-record duplicate query and insertion inside the transaction where possible.

Use an appropriate PostgreSQL transaction isolation level supported by the installed Prisma/PostgreSQL stack.

Preferred if supported:

```text
Serializable
```

because two administrators could import similar candidates concurrently.

If serializable transaction support is used:

* handle known serialization conflicts
* a very small bounded retry is acceptable for the DATABASE transaction only
* do NOT rerun Gemini
* do not retry arbitrary errors

If this is not compatible with the current project, document the chosen race-safety mechanism.

---

# 36. NETWORK RETRY SAFETY

A user may click Import, lose connection, then retry.

The second request must not create obvious duplicate content.

Because commit re-runs DB duplicate detection:

```text
first request succeeded
second request repeats
→ previously inserted content is detected
→ skipped
```

This provides content-level idempotency without an AI session table.
