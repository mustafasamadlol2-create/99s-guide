Fix the Focus Hub synchronization, loading performance, and stale-data behavior across the entire Focus system.

Current problems:
- Focus Hub can take around 5–6 seconds to load.
- Some Focus data does not update immediately after an action.
- The UI can remain stale until a manual Retry/refresh is used.
- There is a Retry button in the Active Focus page.
- The experience feels like a website that needs refresh instead of a native app.

I want Focus Hub to behave like the rest of the application: immediate, automatically synchronized, and with no manual refresh button.

1. Remove manual Retry / refresh
- Remove the Retry button from the Focus UI.
- The user must never need to manually refresh Focus state.
- Do not replace it with another refresh button.
- Recovery, refetching, and reconciliation must happen automatically.

2. Immediate UI synchronization
After any Focus action such as:
- Start Focus
- Pause
- Resume
- Start/finish/skip break
- End Focus
- change session
- move to next lecture
- update the Focus plan
- change planned session count
- add/remove/reorder a lecture
- Quick Notes changes relevant to the view
- resource handoff/return
the visible UI must update immediately.

Use the mutation response to update the local UI immediately, then reconcile with the canonical server state.

Do not wait several seconds for a later full-page reload.

3. Real-time invalidation
Use the application's existing realtime infrastructure, especially Socket.IO, to push Focus-related invalidation/state-change events to the user's other active clients/views.

When Focus data changes:
- update the current client immediately from the successful API response;
- broadcast a lightweight realtime invalidation/state event;
- other open views should automatically refetch/reconcile the affected Focus data.

Do not perform per-second realtime database writes.

The timer must remain timestamp-derived.

4. Database architecture
Keep Supabase PostgreSQL as the canonical durable database.

All canonical Focus writes must continue to be written safely to PostgreSQL/Supabase.

However, the browser/client must NOT directly query Supabase for Focus Hub data.

The normal Focus read path should be:

Client
→ existing application API / Cloudflare read layer
→ D1 Focus read model / cache where appropriate
→ PostgreSQL fallback only when the projection is missing, stale, incomplete, or requires canonical verification.

The goal is to greatly reduce repeated PostgreSQL/Supabase reads, not to create a second source of truth.

PostgreSQL/Supabase remains authoritative.

5. Cloudflare usage
Use each Cloudflare service only where appropriate:

- D1:
  structured Focus Hub read models/projections, plan summaries, safe Focus state snapshots, history summaries, and other relational read-heavy Focus data.

- R2:
  binary/object storage only when genuinely required.
  Do NOT move relational Focus records into R2.
  Do NOT upload the user's local Focus Audio files merely for this optimization.

- existing Worker:
  internal Focus read/projection endpoints and D1 access where appropriate.

- existing outbox/projection architecture:
  use it to keep D1 synchronized from canonical PostgreSQL writes.

Do not create a second user identity or second canonical Focus database in Cloudflare.

6. Fast read-after-write behavior
D1 projection delay must not make the UI look stale.

After a successful canonical Focus mutation:
- return the updated canonical state in the API response;
- immediately update the frontend cache/state;
- trigger the corresponding D1 projection/outbox update;
- push realtime invalidation;
- reconcile automatically in the background.

If D1 has not caught up yet, never overwrite newer local/canonical state with an older D1 snapshot.

Use revisions/timestamps/version ordering to prevent stale projection data from winning.

7. Focus Hub initial load
Investigate why Focus Hub currently needs several seconds to open.

Optimize the complete load path:
- remove unnecessary sequential requests;
- parallelize independent reads;
- eliminate N+1 queries;
- avoid fetching data the initial screen does not need;
- reuse cached/read-model data;
- deduplicate duplicate requests;
- avoid repeated authentication/session resolution;
- eliminate unnecessary blocking projection checks.

The Focus Hub shell should appear immediately and useful Focus state should populate as quickly as possible.

Do not block the entire page because one secondary Focus request is slow.

8. Automatic recovery
Handle automatically:
- temporary network loss
- stale D1 projection
- app background → foreground
- PWA resume
- Capacitor resume
- reconnect
- outdated local state

On reconnect/resume:
- automatically reconcile with the server;
- update the UI;
- do not show Retry unless there is a truly unrecoverable terminal error.

9. Data integrity
Do not sacrifice correctness for speed.

Required rules:
- PostgreSQL/Supabase remains canonical.
- D1 is a derived read model/cache.
- canonical writes must not depend solely on D1 or an async queue.
- no per-second database writes.
- preserve idempotency.
- preserve Focus lifecycle validation.
- preserve user ownership/security.
- preserve Study Points and Mastery rules.
- do not change Schedule behavior.

10. Performance target
Make Focus Hub feel comparable to the fast parts of the existing app.

The user should no longer experience a 5–6 second blank/stale wait for normal Focus Hub navigation.

Use immediate cached/read-model rendering where safe, then silently reconcile in the background.

There must be:
- no manual refresh workflow;
- no stale UI after successful Focus actions;
- no unnecessary direct client → Supabase reads;
- no unnecessary full-page reloads.

Verify on:
- desktop/PWA
- iPhone/Capacitor
- iPad
- multiple open tabs/devices
- network disconnect/reconnect
- background/foreground
- light/dark mode
- English/Arabic

At the end report:
- root causes of the slow/stale Focus behavior;
- files modified;
- Focus data moved to/reused from D1 read models;
- canonical PostgreSQL write path;
- realtime synchronization flow;
- removed Retry UI;
- measured before/after Focus Hub load behavior;
- tests/build/typecheck results.
