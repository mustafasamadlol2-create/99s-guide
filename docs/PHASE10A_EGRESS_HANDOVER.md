# Phase 10A Supabase Egress handover

## Evidence and scope

The production baseline was the owner-verified commit 895a6c6. Its Render liveness and readiness probes returned HTTP 200. Private cutover flags, per-route hit rates, traffic distributions, production outbox delivery, and current Supabase billing were outside the available authenticated observations. The reported 4.6 GB is historical owner evidence. Repository configuration describes possible routing and does not establish live flag values.

Phase 10A keeps PostgreSQL write authority, existing Cloudflare projections, R2 object paths, KV personalization, and Durable Object room state. It narrows PostgreSQL reads and mutation results, scopes the existing browser response and in-flight caches, and adds in-process observations. It requires no new database schema, projection, maintenance job, or polling interval.

## Local measurements

The disposable PostgreSQL fixture ran against the current Prisma schema and rolled back synthetic changes. It compared the previous and optimized selections against the same workload. Serialized result bytes are estimates of application data, excluding the PostgreSQL wire protocol, compression and billing overhead.

| Scenario | SQL statements | Returned rows | Serialized result bytes |
|---|---:|---:|---:|
| Q&A fallback with two questions and 200 visible replies | 5 → 1 | 207 → 4 | 178,190 → 38,586 |
| Analyzer MCQ and flashcard evidence | 6 → 2 | 205 → 205 event rows | 391,161 → 77,101 |
| Content retry upsert | 1 → 1 | 1 → 1 | 29,700 → 32 |
| Notification ownership and delete | 2 → 2 | 2 → 2 | 4,307 → 51 |
| Legacy PDF persistence acknowledgement | 1 → 1 | 1 → 1 | 262,149 → 0 raw blob bytes returned |

The Q&A response remained 98,031 bytes in the fixture. Analyzer output also matched. The access and cache tests demonstrate same-scope in-flight deduplication and reject results completing after an account or cache-generation change. Recurring production frequencies and provider-billed savings remain unmeasured.

## Initial operating budgets

Use these per-event or per-request budgets until production rates can be joined with provider billing. They are guardrails for diagnosis, not forecasts.

| Category | Provisional budget | Evidence and a useful trigger |
|---|---|---|
| Canonical authorization | One narrow canonical authorization result per protected request | Shared session gate. Investigate duplicate profile hydration separately from authorization misses |
| Canonical writes | Acknowledge with the ID, status, revision or actual DTO fields required by the caller | Notification deletion, Q&A mutations, content retries and legacy blob writes require no echoed content they discard |
| Projection synchronization | Payload only for claimed or direct writes. Zero payload bytes for an empty poll. One delivery for equivalent unclaimed snapshots when eligible | Compare private/content send bytes, delivery acknowledgements, retry rates and publication counts over the same window |
| PostgreSQL fallback | Use the smallest contract-preserving fallback. Track by feature, time and reason before setting a hit-rate target | A single busy fallback route can outweigh high D1 hit counts elsewhere. Strict cutover failures keep their existing semantics |
| Scheduled jobs and readiness | Bounded account window, ID or aggregate results as applicable. One scalar database readiness result | Weekly Phase 9B fixture measured two IDs plus total per two-account window. Do not treat poll counts as response bytes |
| Legacy storage | Zero PostgreSQL file body bytes for R2 delivery, HEAD and validated not-modified responses. Requested body bytes for legacy range reads | Transactional legacy PDF reader plus blob byte counter. Inventory legacy access before deciding on a storage migration |
| Admin and one-time operations | Scoped and individually budgeted. Report maintenance separately from student traffic | Usage and response sizes vary with operator action. Compare before/after over equivalent operations |

## Phase 10B verification steps

1. Compare the same billing-cycle segment and similar active-user and workload mix. Use Supabase provider Egress as the billing reference. Historical cumulative PostgreSQL statistics do not establish current traffic.
2. Inspect authorized owner study health at /api/admin/study-health. The existing rolling window now includes route counts and fixed Egress categories. Null byte totals indicate unmeasured bytes. Private Worker result and sync bytes describe application payloads and exclude protocol/TLS overhead. A Gamification enqueue observation includes reused revisions, while delivered counts require the existing fenced acknowledgement.
3. Compare content and private D1 response-source counts with successful PostgreSQL fallback counts, errors, and strict cutover behavior. Some D1 responses still perform canonical security or validation reads. Check reason counters and existing Leaderboard measurements before deciding whether any flag is appropriate.
4. Validate one ordinary student workload with permission. Open a lecture and its Q&A, verify block visibility and votes, read a notification, view a PDF, open Study Analyzer, and check an ordinary study action in Gamification. Check account switching and the relevant existing native routes without exposing student records in logs.
5. Confirm the tested frontend asset and Render revision. Record any auto-generated deployment version separately. Roll back the backend to 895a6c6 and restore the previous frontend version if the release needs reversal. Existing database records and outbox payloads stay compatible with that revision.
